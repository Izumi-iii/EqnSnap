# EqnSnap v0.1 pix2tex 模型方案

> 更新日期：2026-07-16  
> 文档状态：转换前规划  
> 应用集成：[v0.1-integration.md](v0.1-integration.md)

## 1. 结论

v0.1 直接使用 pix2tex 官方预训练权重，不从头训练，也不在尚未建立测试集前进行微调。

原因：

- 当前产品只处理清晰、常规、单行印刷公式。
- 本机 Python 基线样本已经能够正确识别，且模型规模明显小于 UniMERNet-Tiny。
- 首要未知量是 Core ML 转换后的算子兼容、精度、延迟、内存和包体，而不是训练能力。
- 没有冻结的数据集时进行微调，无法判断质量是否真的改善，也容易破坏模型原有能力。

只有 v0.1 测试集显示目标场景存在集中、可复现且无法通过预处理或解码策略解决的错误时，才进入微调评估。

## 2. 固定版本与环境

当前项目使用：

```text
pix2tex==0.1.4
coremltools==9.0
```

现有依赖文件位于：

```text
Tools/model-conversion/requirements.in
Tools/model-conversion/requirements.txt
```

当前依赖中的 PyTorch 2.7.1 高于 coremltools 9.0 已明确测试到的 2.7.0。转换环境应优先建立一个独立、可复现的组合进行验证：

```text
torch==2.7.0
torchvision==0.22.0
coremltools==9.0
pix2tex==0.1.4
```

这只是优先尝试方案，不能保证所有 pix2tex 依赖与导出路径无需调整。最终必须把成功环境锁定到 requirements 和转换记录中。

每次导出记录：

- Python、macOS 和芯片版本。
- pix2tex、PyTorch、torchvision、coremltools 版本。
- 原始 checkpoint SHA-256。
- 转换脚本 Git commit。
- 转换精度 FP32/FP16/8-bit。
- Core ML compute units 和最低部署版本。

## 3. 模型组成

pix2tex 0.1.4 的应用链路可拆为：

```text
公式图片
  → 空白裁切与尺寸处理
  → 可选 Image Resizer
  → ResNetV2 + Hybrid ViT Encoder
  → x-transformers 自回归 Decoder
  → Tokenizer
  → LaTeX 字符串
```

### 3.1 Image Resizer

- 用于预测更适合的公式输入宽度。
- 增加一个模型和约 19 MB FP32 权重。
- 可能提高不同长宽比公式的识别质量，也增加转换和运行复杂度。

v0.1 需要用测试集对比两条路径：

1. 复现官方 Image Resizer。
2. Swift 规则裁边并缩放/补白到受限画布。

不能仅因包体更小就删除 Resizer，也不能在没有对比数据时默认它必须存在。

当前严格单行子集的诊断结果表明：完全关闭 Resizer 会使稳定对照样本明显退化；但官方 Resizer 对部分短公式保留了过大的有效尺度，导致 Encoder 产生高置信错误特征。将前景相对缩小到 0.75 在 Layer 1 上显著改善，但在 Layer 2 的 light、dark 和 degraded 截图风格上未通过验证，因此不能作为跨来源的通用规则，也不能据此删除或替代 Resizer。

### 3.2 Encoder

- 输入单通道公式图像。
- ResNetV2 提取局部特征。
- Hybrid Vision Transformer 输出 Decoder 使用的视觉 context。
- 每张截图只执行一次。

转换重点：动态尺寸、Hybrid Embedding、位置编码/索引和注意力算子。

### 3.3 Decoder

- 输入 Encoder context 和已生成的 Token。
- 自回归输出下一个 Token 的 logits。
- 遇到 EOS 或达到最大长度时结束。
- 官方最大序列长度为 512，产品实际限制需根据单行测试集决定。

官方实现使用 Top-K、temperature 约 0.2 和随机采样。桌面复制工具更重视结果可复现，因此必须比较：

- 官方采样：尽量复现 Python 输出分布。
- Argmax：每次取最大概率 Token，结果确定。

选择依据是测试集完整正确率和人工可接受率，而不是只比较单个公式。

### 3.4 Tokenizer

Tokenizer 是模型的一部分，不是普通字符串表：

- Token ID 必须与 checkpoint 对应。
- BOS、EOS、PAD 和未知 Token 必须固定。
- 解码和空格处理必须与 Python 基线一致。
- `tokenizer.json` 需要和模型版本共同发布及校验。

## 5. 输入策略

### 5.1 输入候选验证结论

固定大画布方案已经被严格单行子集否定。实验扫描了 `448×64` 画布中的多个固定前景高度；最佳固定高度仍会造成大量长错误输出，因此不能把所有公式统一补到单一大画布。

Layer 1 上曾验证以下候选规则：

```text
任意公式截图
  → 裁除外围空白
  → 使用 pix2tex 黑白前景归一化
  → 保持长宽比，将裁切结果相对缩放到 0.75
  → 左上角放置到白色画布
  → 宽度和高度分别向上补到 32 的倍数
  → 限制在 672 × 192 范围内
  → 使用 pix2tex test_transform 生成单通道张量
```

严格子集 176 条样本中观察到 22 种输入 shape：高度主要为 32 或 64，宽度主要为 128–384；只有一条达到 96 高。这个方案在 Layer 3 真实截图上基本持平，但在 Layer 2 三种截图风格上明显失败，说明相对缩放依赖来源图片的原始字号。

当前没有通过全部三层验证的生产输入契约。现有 `64×448` Encoder 继续保留为数值转换 fixture，不再视为生产模型；0.75 相对缩放也降级为已否定的单层实验结果。

下一步必须先评估：

- 根据裁切后的实际前景像素高度缩放到统一目标高度。
- 缩放后只补到最近的 32 倍数 shape，不统一补到 `448×64`。
- 在 Layer 1、Layer 2 和 Layer 3 上共同选择目标高度。
- 通过后再评估 `EnumeratedShapes` 和 flexible Decoder context。

该实验已完成：24 px 能让 Layer 1 和 Layer 2 三种风格稳定在约 0.71–0.72，且没有长度膨胀；但 Layer 3 真实截图下降到约 0.536。提高到 28–40 px 会逐步改善部分真实截图，却会让 Layer 1/2 出现更多错误和长度膨胀。

因此当前仍没有跨三层通过的单一目标高度。下一步需要研究可从图像本身估计的有效笔画尺度，或少量可判定的预处理 profile；不能按数据集来源硬编码分支。通过前继续暂停生产用途的 Encoder 和单步 Decoder 改造。

### 5.2 预处理必须对齐

Python 和 Swift 需要逐项固定：

- 前景/背景判断和裁边阈值。
- 裁切时保留的 padding。
- 等比例缩放算法和插值方式。
- 白色补边位置。
- 灰度转换公式。
- 像素取值范围。
- mean、standard deviation。
- NCHW/NHWC 布局和数据类型。

先导出固定图片的预处理张量 fixture，再实现 Swift。不得根据视觉上“看起来一样”判断数值一致。

## 6. Decoder 转换策略

### 6.1 正确性优先版本

第一版 Decoder 接收：

```text
encoder_context
input_ids
attention_mask 或 sequence_length
```

输出当前有效位置的 logits。可使用 Core ML flexible shape 或固定容量加显式有效长度，具体以 coremltools 转换可行为准。

第一阶段允许每一步重新计算完整 Token 前缀。这样实现简单、便于与 PyTorch 对照，但可能达不到性能目标。

### 6.2 性能版本

只有正确性版本 P95 延迟不达标时，再评估：

- KV Cache 输入/输出。
- 按长度预编译多个 Decoder shape。
- 降低经测试仍足够的最大输出长度。
- 将部分采样或 mask 逻辑移到 Swift。

KV Cache 会增加状态张量和转换复杂度，不应在尚未跑通单步 Decoder 前实施。

## 7. 转换阶段

### M0：冻结 Python 基线

- 下载并校验官方 checkpoint 与 tokenizer。
- 固定 100–300 张目标样本。
- 保存输入、Python 输出 Token、LaTeX 和耗时。
- 设置随机种子并分别记录采样与 Argmax 结果。

### M1：模型结构探测

- 打印每个模块的输入/输出 shape 和 dtype。
- 确定 Encoder context、词表大小和特殊 Token。
- 确认动态控制流、mask 和位置编码路径。

### M2：Image Resizer 转换

- 单独转换并比较宽度分类 logits/结果。
- 记录有无 Resizer 的质量与耗时。
- 若固定画布质量相当，可从 App Bundle 中移除该模型。

### M3：Encoder 转换

- 先用 FP32 CPU_ONLY 验证数值。
- 再转换 FP16 并测试 CPU_AND_NE 或 ALL。
- 比较输出 shape、最大绝对误差、平均绝对误差和 cosine similarity。

### M4：Decoder 单步转换

- 使用 Python 保存的 context 和 Token 前缀测试单步 logits。
- 覆盖序列开头、中段、接近 EOS 和较长前缀。
- 检查 causal mask 和 padding 是否一致。

### M5：Core ML 端到端循环

- 使用 Core ML Encoder context 驱动 Core ML Decoder。
- 比较完整 Token 序列和最终 LaTeX。
- 分别运行官方采样与 Argmax。

### M6：Swift 原型

- 读取 manifest 和 tokenizer。
- 实现 Swift 预处理与 Decoder 循环。
- 使用相同 fixtures 复现 Python/Core ML 结果。

### M7：压缩与性能

- FP32 仅用于数值基线。
- FP16 作为第一发布候选。
- 8-bit 权重量化必须重新跑完整测试集。
- 记录模型加载、预处理、Encoder、每 Token Decoder、总耗时、峰值内存和包体。

## 8. 质量评估

### 8.1 测试集分层

| 层级 | 示例 |
|---|---|
| 简单 | 单变量、上下标、简单等式 |
| 一般 | 分式、根号、积分、求和、希腊字母 |
| 较长 | 多层上下标、多个运算符、长单行表达式 |
| 图像退化 | 小字号、轻度模糊、深色模式、抗锯齿差异 |
| 超出范围 | 手写、矩阵、多行公式、文字混排 |

超出范围样本用于了解失败方式，不计入 v0.1 支持场景的主指标。

### 8.2 指标

- 原始字符串 exact match。
- 经过明确规范化规则后的 normalized match。
- Token edit distance。
- 人工可接受率：渲染语义正确但字符串形式不同。
- 空结果、重复循环、未闭合命令和超长截断比例。
- P50/P95 延迟与峰值内存。

规范化规则必须版本化，例如空白、等价括号或 `\left/\right` 处理；不能用过强规范化掩盖真实错误。

### 8.3 发布门槛

模型门槛应在测试集形成后写入具体数值。当前不凭少量样本预设一个看似精确的准确率。

至少要求：

- Core ML 相对 Python 基线没有系统性漏符号或重复 Token。
- 常见公式类型不存在集中崩溃或无限循环。
- 同一确定性配置重复运行结果一致。
- 超长输出能够安全停止并返回可理解错误。

## 9. 何时考虑微调

满足以下条件后才考虑：

1. Core ML 与 Python 基线已经对齐，排除转换错误。
2. 预处理、画布和解码策略已经完成对比。
3. 至少有数百张与产品场景一致、许可明确的训练/验证样本。
4. 错误集中在可描述类别，例如特定字体、深色模式或某类符号。
5. 有独立验证集，能够检查微调是否损害其他公式类型。

优先顺序：

```text
修复转换/预处理
  → 调整解码策略
  → 扩充评测数据
  → 小规模 fine-tune
  → 只有充分证据时才考虑从头训练
```

## 10. 商业与许可证检查

pix2tex Python 包采用 MIT License，通常允许闭源商业使用，但发布前仍需逐项核对：

- 仓库代码许可证。
- checkpoint/权重的分发条款。
- tokenizer 和词表来源。
- x-transformers、timm 等转换期或运行期依赖。
- LaTeX 渲染库许可证。
- Snapio 迁移代码的所有权。

App 内应提供第三方声明并保留所需版权文本。此文档是工程合规清单，不替代正式法律意见。
