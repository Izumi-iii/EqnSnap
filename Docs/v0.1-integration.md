# EqnSnap v0.1 模型与 Swift 集成契约

> 更新日期：2026-07-16  
> 文档状态：接口规划稿  
> Swift 架构：[v0.1-swift-architecture.md](v0.1-swift-architecture.md)  
> 模型转换：[v0.1-model.md](v0.1-model.md)

## 1. 目的

本文件定义 Python 模型转换产物与 macOS Swift 应用之间的唯一边界，防止以下问题：

- Python 调整了输入尺寸，Swift 仍使用旧常量。
- Tokenizer、模型权重和特殊 Token 不匹配。
- Core ML 输入/输出名称改变后只能在运行时崩溃。
- UI 或业务层直接依赖某个 pix2tex Core ML 类，导致以后无法替换模型。

原则：模型细节收口在 `EqnSnapRecognition`，其余模块只依赖 `FormulaRecognitionPort`。

## 2. 产物边界

Python 转换流程交付：

```text
Pix2TexEncoder.mlpackage / .mlmodelc
Pix2TexDecoder.mlpackage / .mlmodelc
Pix2TexImageResizer.mlpackage / .mlmodelc   # 可选
tokenizer.json
model-manifest.json
LICENSES/
```

Swift 不读取 PyTorch checkpoint，不导入 Python 包，也不推断缺失的配置。任何运行所需参数都必须出现在模型 spec、Tokenizer 或 manifest 中。

## 3. Manifest

建议初始结构：

```json
{
  "schemaVersion": 1,
  "modelID": "pix2tex",
  "modelVersion": "0.1.4-coreml-1",
  "minimumMacOS": "13.0",
  "precision": "float16",
  "artifacts": {
    "encoder": {
      "resource": "Pix2TexEncoder",
      "sha256": "..."
    },
    "decoder": {
      "resource": "Pix2TexDecoder",
      "sha256": "..."
    },
    "imageResizer": null,
    "tokenizer": {
      "resource": "tokenizer.json",
      "sha256": "..."
    }
  },
  "image": {
    "colorSpace": "grayscale",
    "canvasHeight": 192,
    "canvasWidth": 672,
    "backgroundValue": 1.0,
    "pixelRange": "zeroToOne",
    "mean": [0.7931],
    "std": [0.1738],
    "layout": "NCHW",
    "resizeMode": "aspectFit",
    "alignment": "center",
    "cropRuleVersion": 1
  },
  "encoder": {
    "inputName": "pixel_values",
    "outputName": "encoder_context"
  },
  "decoder": {
    "contextInputName": "encoder_context",
    "tokenInputName": "input_ids",
    "sequenceLengthInputName": "sequence_length",
    "logitsOutputName": "logits",
    "maxSequenceLength": 512,
    "strategy": "argmax",
    "temperature": 0.2,
    "topK": 10
  },
  "tokens": {
    "bos": 1,
    "eos": 2,
    "pad": 0,
    "unknown": 3
  }
}
```

上例中的 mean、std、Token ID、Top-K 和 Tensor 名称只是结构示例，不能直接作为最终值。它们必须由实际 pix2tex 配置和导出模型生成。

### 3.1 版本规则

- `schemaVersion`：Swift 解析协议版本；不支持时拒绝加载并显示模型不兼容。
- `modelVersion`：权重、转换脚本、Tokenizer 或预处理任一变化都应更新。
- 仅修改不影响输出的描述信息时可不改变模型版本。
- App 记录其支持的 manifest schema 范围。

### 3.2 校验规则

加载时检查：

- 必需资源存在。
- SHA-256 与 manifest 一致。
- Core ML feature 名称、shape 和 dtype 与 manifest 一致。
- Token ID 在词表范围内且互不冲突。
- 最大序列长度和 Decoder 支持的 shape 一致。
- 模型最低系统版本不高于当前运行环境。

开发构建可以在启动时做完整校验；发行构建至少在首次模型加载时校验版本和 feature contract。

## 4. Swift 对外接口

Core 中定义与模型无关的接口：

```swift
struct FormulaRecognitionRequest: Sendable {
    let sessionID: CaptureSessionID
    let image: CGImage
}

struct RecognitionTimings: Sendable, Equatable {
    let preprocessing: Duration
    let encoding: Duration
    let decoding: Duration
    let total: Duration
}

struct FormulaRecognitionResult: Sendable, Equatable {
    let sessionID: CaptureSessionID
    let latex: String
    let tokenCount: Int
    let timings: RecognitionTimings
    let modelVersion: String
}

protocol FormulaRecognitionPort: Sendable {
    func prepare() async throws
    func recognize(_ request: FormulaRecognitionRequest) async throws -> FormulaRecognitionResult
    func cancel(sessionID: CaptureSessionID) async
}
```

`FormulaRecognitionResult` 不包含 `MLMultiArray`、logits 或 tokenizer 对象。调试信息通过 Recognition 内部日志或测试接口获取，不污染产品接口。

## 5. Recognition 内部流程

```text
CapturedFormula(CGImage)
    │
    ▼
FormulaImagePreprocessor
    ├── 灰度/反色策略
    ├── 前景边界裁切
    ├── 等比例缩放
    ├── 固定画布补白
    └── 归一化与 Tensor 排列
    │
    ▼
Pix2TexEncoderRunner
    │ encoder_context
    ▼
Pix2TexDecoderRunner
    ├── BOS 初始化
    ├── causal decode loop
    ├── argmax 或官方采样
    ├── EOS / cancel / max-length 检查
    └── Token IDs
    │
    ▼
Pix2TexTokenizer
    │
    ▼
LatexNormalizer
    │
    ▼
FormulaRecognitionResult
```

### 5.1 预处理

预处理器只读取 manifest 配置，返回内部 `PreparedFormulaInput`：

```swift
struct PreparedFormulaInput {
    let tensor: MLMultiArray
    let sourcePixelSize: CGSize
    let croppedPixelRect: CGRect
}
```

该类型留在 Recognition Target。测试时可通过专用 fixture exporter 检查张量，不向 UI 暴露。

深色模式公式的反色不能简单依赖系统外观。应基于截图像素或明确的预处理规则判断，并用 fixture 验证黑底白字、灰底和透明抗锯齿边缘。

### 5.2 Encoder

- 每次请求只调用一次。
- 输出 context 的 shape 和 dtype 在加载时校验。
- context 只在当前请求中持有。
- 不把 context 存入历史或跨请求缓存。

### 5.3 Decoder 循环

伪代码：

```swift
var tokens = [manifest.tokens.bos]

while tokens.count < manifest.decoder.maxSequenceLength {
    try Task.checkCancellation()
    guard request.sessionID == activeSessionID else {
        throw CancellationError()
    }

    let logits = try decoder.predict(
        context: context,
        tokens: tokens
    )
    let next = decodingStrategy.selectNextToken(from: logits)

    if next == manifest.tokens.eos {
        break
    }

    tokens.append(next)
}
```

还需要处理：

- Decoder 返回 PAD/BOS 等非法下一 Token。
- 连续重复模式和无 EOS。
- logits 中出现 NaN/Inf。
- 超过最大长度时返回截断错误，而不是把不完整字符串当成功结果。
- 官方随机采样时使用可注入随机种子，确保测试可重复。

### 5.4 Tokenizer 与规范化

- Swift Tokenizer 必须通过 Python 生成的 token fixture 验证。
- 解码后先做语法安全检查，再做有限规范化。
- 不自动添加 `$...$`。
- 不擅自把用户宏替换为标准命令。
- 渲染失败不等于识别失败；仍可把源码交给用户修改或复制。

## 6. 并发、线程与取消

建议 `Pix2TexRecognitionService` 使用 actor：

```swift
actor Pix2TexRecognitionService: FormulaRecognitionPort {
    private var models: LoadedModels?
    private var activeSessionID: CaptureSessionID?
}
```

规则：

- 模型加载和一次识别由 actor 串行管理。
- `prepare()` 可在应用启动后低优先级调用，也可首次截图时懒加载。
- UI 状态更新只在 `@MainActor` workflow 中发生。
- Core ML prediction 在独立任务中执行，避免阻塞主线程。
- `Task.cancel()` 不能保证中止正在执行的底层 Core ML 运算，因此完成回调仍要核对 session ID。
- 关闭结果时先使 session 失效，再调用 cancel。

不建议 v0.1 同时并行运行多个 Decoder。

## 7. 模型加载与预热

### 7.1 加载策略

推荐顺序：

1. App 启动后菜单栏立即可用。
2. 后台低优先级读取 manifest 并编译/加载模型。
3. 用户提前触发截图时复用同一加载 task，并显示“正在准备模型”。
4. 加载失败时菜单栏仍可打开设置和许可证信息。

### 7.2 预热

是否执行一次空白/固定样本 prediction 需要实测：

- 若明显降低首次真实识别延迟且内存可接受，则在后台预热。
- 若增加启动功耗或长时间占用资源，则采用首次请求加载。
- 预热样本必须是应用内固定资源，不使用用户截图。

## 8. 错误映射

| Recognition 内部错误 | Core/Presentation 错误 | UI 行为 |
|---|---|---|
| manifest 无法解析 | `modelIncompatible` | 提示应用资源异常，不能重试截图 |
| 模型或 tokenizer 缺失 | `modelResourceMissing` | 提示重新安装应用 |
| shape/feature 不匹配 | `modelIncompatible` | 记录详细日志，显示通用模型错误 |
| 图片为空或前景过小 | `invalidSelection` | 返回截图流程或重新框选 |
| Core ML prediction 失败 | `recognitionFailed` | 保留截图，允许重试 |
| 达到最大 Token 长度 | `outputTooLong` | 保留截图，提示公式可能超出首版范围 |
| 任务/会话取消 | `CancellationError` | 静默关闭，不显示错误 |

## 9. 测试契约

### 9.1 Python 导出 fixtures

每个代表样本至少输出：

```text
fixture-id/
├── input.png
├── metadata.json
├── preprocessed.npy
├── encoder-context.npy
├── decoder-steps/
│   ├── step-000-input-ids.json
│   ├── step-000-logits.npy
│   └── ...
├── expected-token-ids.json
└── expected-latex.txt
```

不需要把所有 100–300 张样本都保存完整中间张量。选择少量覆盖不同尺寸和公式结构的数值 fixtures，其余样本只保存端到端期望结果。

### 9.2 测试层级

1. 预处理张量误差测试。
2. Encoder context 数值测试。
3. Decoder 单步 logits 排名和误差测试。
4. Tokenizer ID/字符串双向 fixture。
5. Core ML 端到端 Token 序列测试。
6. Swift `FormulaRecognitionPort` golden test。
7. 截图到结果浮层的集成测试。

浮点比较阈值由 FP32/FP16 实测确定，不在没有数据时随意填写固定 epsilon。对于 Decoder，除了数值误差，还要检查 top-1 Token 是否一致；很小的 logits 差异可能改变完整序列。

## 10. 性能记录

每次识别本地记录到内存或开发日志：

- 模型是否冷加载。
- 预处理耗时。
- Encoder 耗时。
- Decoder 总耗时和 Token 数。
- 端到端耗时。
- 错误类型。

默认不记录：

- 用户截图。
- LaTeX 字符串。
- Token 序列。
- 来源应用或屏幕内容。

若未来上传诊断信息，必须另行设计明确的用户同意和隐私说明；不属于 v0.1。

## 11. 模型升级与回滚

v0.1 模型随 App Bundle 发布，不做运行时下载。

升级流程：

1. 生成新的模型版本和 manifest。
2. 跑数值 fixtures、完整质量集和性能测试。
3. 检查包体和最低系统版本。
4. 更新第三方声明。
5. 随新的 App 版本发布。

回滚通过恢复上一组模型资源和 manifest 完成。不要只替换 Encoder 或 Tokenizer 中的一部分；一组 artifact 必须作为原子版本发布。

## 12. 替换模型的边界

如果以后 pix2tex 无法满足需求，可以增加：

```swift
actor UniMERRecognitionService: FormulaRecognitionPort { ... }
```

或其他模型实现。截图、菜单栏、结果编辑、复制和 UI 状态不应因此改变。允许变化的边界只有：

- 模型资源和 manifest。
- Recognition 内部预处理。
- Encoder/Decoder 或单体模型运行方式。
- Tokenizer 和结果规范化。
- 模型特有的错误映射。

这就是 v0.1 所需的可扩展性：稳定边界可替换，而不是提前建立一个通用模型插件系统。
