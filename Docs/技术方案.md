# EqnSnap 技术方案：pix2tex + Core ML

> 更新日期：2026-07-16<br>
> 状态：模型选型已确定，等待 Core ML 转换验证

## 1. 产品与技术目标

EqnSnap 首版聚焦以下场景：

- 用户通过全局快捷键框选屏幕中的公式。
- 只识别清晰、常规、单行的印刷体数学公式。
- 输出 LaTeX，并支持预览、修正和复制。
- 不支持手写公式、复杂多行公式、矩阵、整篇文档 OCR 或云端增强。
- 识别过程完全在本机运行，发布版本不依赖 Python。
- 应用使用 Swift、SwiftUI 和必要的 AppKit，模型使用 Core ML。

目标链路：

```text
全局快捷键
    → 框选单行公式
    → Swift 图像预处理
    → Core ML 图像编码
    → Swift 驱动 Core ML 自回归解码
    → Token ID 转 LaTeX
    → 预览和复制
```

## 2. 模型选型

项目确定采用 [pix2tex / LaTeX-OCR](https://github.com/lukas-blecher/LaTeX-OCR) 作为首版识别模型。

选择依据：

- 项目自己的单行积分公式测试识别正确，连续三轮输出一致。
- Apple M4 CPU 平均推理约 0.56 秒，模型加载约 0.42 秒。
- 主识别模型和图片尺寸预测器合计约 30.35M 参数、115.9 MB FP32 权重。
- 理论 FP16 权重约 58 MB，明显适合轻量 macOS 工具。
- 当前业务主动不承诺复杂多行公式和矩阵，pix2tex 在这些场景中的精度不足不属于首版验收范围。
- 官方 Python 包标记为 MIT License，原则上允许闭源商业使用。

选型时也测试了更大的 UniMERNet-Tiny。它在复杂公式上更可靠，但约 107.4M 参数、430 MB FP32 权重，不符合当前轻量单行公式产品的优先级，因此暂不采用。

## 3. pix2tex 模型结构

当前 `pix2tex 0.1.4` 默认配置包含三部分：

### 3.1 图片尺寸预测器

- 使用 ResNetV2。
- 根据输入公式预测合适的宽度，宽度按 32 像素对齐。
- 参数量约 4.85M，FP32 权重约 19 MB。
- 最终产品可以先转换该模型，也可以尝试用 Swift 固定规则代替，但替代后必须重新测试精度。

### 3.2 视觉 Encoder

- 使用 ResNetV2 Backbone 提取局部视觉特征。
- 使用 Hybrid Vision Transformer 将视觉特征编码为序列表示。
- 默认处理单通道灰度图像。
- 最大输入范围为 192 × 672，最小范围为 32 × 32。

### 3.3 LaTeX Decoder

- 使用基于 `x-transformers` 的自回归 Transformer Decoder。
- 默认最大序列长度为 512。
- Decoder 逐 Token 读取 Encoder 特征并生成 LaTeX。
- 官方实现使用 Top-K 过滤、Softmax 和随机采样，默认温度约 0.2，因此复杂公式的结果可能存在随机性。

首版产品更需要稳定输出。转换阶段应分别验证：

1. 完全复现官方采样逻辑。
2. 使用 Argmax 的确定性贪心解码。

只有在内部单行公式测试集上确认精度没有明显下降后，才能切换到确定性解码。

## 4. 图像预处理

官方推理流程包括：

1. 裁剪公式周围的空白区域。
2. 根据最大、最小尺寸进行等比例缩放和补白。
3. 可选调用图片尺寸预测器调整公式宽度。
4. 转换为单通道灰度张量。
5. 按训练时使用的均值和标准差归一化。

Swift 版本必须与 Python 基线对齐以下细节：

- 裁边阈值和边界范围。
- 缩放插值算法。
- 补白颜色和位置。
- 灰度转换方法。
- 归一化参数和张量布局。

需要保存固定输入图片的 Python 中间张量，与 Swift 结果逐元素比较。

## 5. Core ML 拆分方案

不建议把完整的 Python `LatexOCR.__call__()` 直接转换为单个模型。建议拆分为：

### 5.1 可选 Image Resizer

```text
输入：公式灰度图像
输出：建议宽度档位
```

第一阶段可以先保留官方 ResNetV2 尺寸预测器，以减少精度变量。模型主链路稳定后，再评估是否由 Swift 规则替代并移除约 4.85M 参数。

### 5.2 Encoder

```text
输入：pixel_values
输出：context / encoder_hidden_states
```

Encoder 每张截图只执行一次。转换重点是 ResNetV2、Hybrid Embedding、位置索引和 Vision Transformer 注意力。

### 5.3 Decoder

```text
输入：
  - encoder context
  - 已生成的 Token 序列

输出：
  - 下一个 Token 的 logits
```

Swift 从 BOS Token 开始循环调用 Decoder，遇到 EOS 或达到最大长度后结束。第一版先使用完整 Token 序列作为 Decoder 输入，确认输出正确后再评估 KV Cache 或其他性能优化。

## 6. Swift 端职责

发布的纯 Swift 应用至少需要实现：

- 全局快捷键、框选截图、Esc 取消和多显示器支持。
- 与 Python 一致的图像裁剪、缩放、补白、灰度和归一化。
- 可选的图片尺寸预测器调用。
- Core ML Encoder 调用。
- Decoder 自回归循环、EOS 判断和最大长度限制。
- Top-K 采样或确定性 Argmax 解码。
- 与官方 `tokenizer.json` 一致的 Token ID 解码。
- LaTeX 结果预览、编辑和剪贴板写入。
- 空白截图、过小图片、超长输出和模型加载失败处理。

“纯 Swift”只描述应用运行时。模型转换、数值对照和基准测试仍使用 Python、PyTorch 和 `coremltools`。

## 7. 商业合规

pix2tex 0.1.4 Python 包携带 MIT License，允许商业使用、修改、再分发和闭源集成。

发行前仍需：

- 在第三方开源声明中保留 MIT License 和版权声明。
- 核对最终分发的权重、Tokenizer、转换代码和所有第三方资源。
- 记录对模型和预处理代码所做的修改。
- 不把开源许可证视为对训练数据、专利或所有商业风险的法律保证。

## 8. 已知风险

| 风险 | 影响 | 处理方式 |
|---|---|---|
| Decoder 默认随机采样 | 同一复杂公式输出可能变化 | 对比官方采样与 Argmax，首版优先稳定性 |
| Transformer Decoder 自回归较慢 | 长公式延迟上升 | 限定单行场景，之后评估 KV Cache |
| Hybrid ViT 动态位置索引转换失败 | Encoder 无法直接导出 | 固定支持的输入尺寸并逐层转换 |
| Swift 预处理与 Python 不一致 | 精度下降 | 对中间张量做逐元素回归测试 |
| 简单公式之外精度不足 | 用户超出产品边界时结果较差 | UI 和产品文案明确首版范围 |
| Core ML 量化导致精度下降 | 模型虽小但识别错误增加 | FP16 正确后再测试 8-bit |
| macOS 13 算子或 API 限制 | 最低系统版本无法运行 | 始终在 macOS 13 目标环境验证 |

## 9. 转换和验证顺序

1. **已完成**：pix2tex PyTorch 本机基线，项目公式 CPU 平均推理约 0.56 秒。
2. 固定 50–100 张清晰单行公式作为首版验收集。
3. 导出图片尺寸预测器，并验证 Core ML 与 PyTorch 输出一致。
4. 导出 Encoder，并比较特征张量误差。
5. 导出单步 Decoder，并比较每一步 logits 和最终 Token 序列。
6. 在 Swift 命令行原型中实现预处理、Tokenizer 和解码循环。
7. 测试 FP16 模型的文件大小、P50/P95 延迟和峰值内存。
8. 在 FP16 基线正确后测试 8-bit 权重量化。
9. 达到验收标准后再开发完整截图交互和 SwiftUI 界面。

建议首版模型验收标准：

- 清晰单行印刷公式完整正确率达到内部目标。
- 普通公式端到端延迟达到可即时使用的水平。
- 模型包体积优先控制在约 60 MB；若使用 8-bit，可进一步争取约 30 MB。
- 模型常驻内存适合菜单栏工具。
- 不依赖网络和 Python 运行时。
